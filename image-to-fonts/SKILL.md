# Image to Fonts — 견본 시트 이미지 → OTF 폰트

검증된 파이프라인: 이진화 → 연결요소 분리(점·조각 병합) → 행/기준선 추정 → 벡터 추적(윤곽 걷기 + 코너 보존형 스무딩 + 닫힌 RDP) → em 좌표 반올림 후 2차 정리 → 대문자 700 정규화 → 광학 오버슈트/사이드베어링 보정 → opentype.js로 OTF 패키징. 오버슈트(O가 기준선 아래로 살짝 내려감)와 플러리시(Q 꼬리 등)는 형태를 그대로 따라 그리므로 자동 보존된다.

## 0단계 — 반드시 폰트 이름부터 물어본다

이미지가 도착하면 작업 시작 전에 **폰트 이름을 먼저 질문**한다 (예: "폰트 이름을 뭐로 할까요?"). 영문 전용이면 영문 이름을 권장한다 — 한글 이름으로 하면 포토샵 등에서 폰트 목록에 투명하게(이름이 안 보이게) 뜨는 현상이 있다. 이름을 받은 뒤 진행한다. 사용자가 이미 이름을 말했다면 그대로 쓴다.

이때 함께 확인: 저작권 있는 상용 폰트 견본이면 개인 학습/실험 용도로만 쓰도록 한 줄 안내 (이미 알고 있는 사용자면 생략).

## 1단계 — 해상도 확인 (근본적으로 가장 중요)

**"크게 보면 울퉁불퉁하다", "글자마다 크기가 다르다" 같은 피드백의 90%는 알고리즘이 아니라 원본 해상도 부족이 원인이다.** 실측: 글자 높이 85px 시트와 500px 시트를 같은 글자로 비교하면, 스무딩 이전 원본 추적 데이터의 점 개수가 201개 vs 575개(2.9배) 차이 났다 — 저해상도는 곡선을 그릴 재료 자체가 부족하다.

- 이미지를 받으면 먼저 `img2bin.py`로 변환된 크기(W, H)와 대략 몇 행/몇 열 그리드인지로 글자당 픽셀 높이를 가늠한다.
- **글자 높이가 150px를 한참 밑돌면(특히 80~100px대)**, 작업을 진행하되 "크게 확대하면 다소 거칠 수 있다"고 미리 안내하거나, 가능하면 "글자 높이 300px 이상으로 다시 촬영/내보내서 재업로드해달라"고 먼저 요청하는 편이 낫다.
- 대문자 시트 + 소문자 시트처럼 여러 장으로 나눠 받아도 된다 — 아래 "여러 시트 병합" 절차로 하나의 폰트로 합친다.
- `img2bin.py`의 리사이즈 상한은 3400px(가로/세로 큰 쪽 기준)다. 이보다 큰 원본을 받으면 이 상한 안에서 최대한 활용된다.

## 2단계 — 이미지 분해

```bash
cd <이 스킬의 scripts 폴더>
python3 img2bin.py <업로드이미지> /tmp/ff/sheet.bin   # 출력: W H
node pipeline.js segment /tmp/ff/sheet.bin <W> <H> /tmp/ff/work
```

segment 출력 JSON의 `count`와 `standard`를 확인:

- **`standard: true` (26/52/62개)** → 알파벳순 시트로 판단. 읽는 순서대로 라벨 자동 생성:
  - 26개 = `A~Z`, 52개 = `A~Z a~z`, 62개 = `A~Z a~z 0~9`
  - labels.json 작성: `{"0":"A","1":"B",...}` (comps.json의 i 순서 = 읽는 순서)
- **`standard: false`** → 시트에 제목·장식·샘플문구가 섞였거나 단어 견본. **절대 순서 라벨을 강행하지 말 것** (한 칸만 밀려도 폰트 전체가 깨진다). 대신:
  ```bash
  python3 contact_sheet.py /tmp/ff/work /tmp/ff/contact.png
  ```
  → **contact.png를 view 도구로 직접 보고**, 각 번호 칸의 글자를 눈으로 판별해 labels.json을 작성한다. 장식·판독불가는 `"skip"`. 같은 글자가 여러 번 나오면 가장 깨끗한 것 하나만 글자로, 나머지는 `"skip"`. (`"?"`는 실제 물음표 글자로 들어가니 버리는 조각에 쓰지 말 것)
  - 행 구조가 보이면 활용하라: 알파벳 시트인데 앞뒤에 헤더/샘플 행이 끼어든 경우, 13개짜리 행 4개(= A-M / N-Z / a-m / n-z)를 찾으면 그 행들만 순서 라벨하고 나머지 행은 전부 `"skip"` 처리하면 된다.
  - 단어 견본(예: "MODERN SERIF")이면 등장한 글자만 폰트에 들어간다는 사실을 사용자에게 미리 알린다.

### 여러 시트 병합(예: 대문자.png + 소문자.png)

```bash
python3 img2bin.py 대문자.png /tmp/ff/upper.bin   # 출력: W H
python3 img2bin.py 소문자.png /tmp/ff/lower.bin   # 출력: W H
node pipeline.js segment /tmp/ff/upper.bin <W1> <H1> /tmp/ff/work_upper
node pipeline.js segment /tmp/ff/lower.bin <W2> <H2> /tmp/ff/work_lower
```

두 결과의 `comps.json`을 병합한다(크롭 인덱스를 겹치지 않게 재번호 매기고 crops 파일도 복사), 병합된 `labels.json`(대문자 인덱스→A-Z, 소문자 인덱스→a-z)을 작성한 뒤 **build는 한 번만** 돌린다. 이렇게 해야 대문자 기준 스케일(capMed)이 두 세트에 일관되게 적용된다. (예시 병합 스크립트는 이전 세션 기록 참고 — Python으로 두 `comps.json` 배열을 이어붙이고 `crops/` 파일을 복사하면 된다.)

### 숫자·기호 시트

라벨에는 영문·숫자뿐 아니라 **한 글자짜리 기호도 그대로** 쓸 수 있다(`"!"`, `"@"`, `"?"`, `"’"` 등). 글리프 이름은 `exclam`, `at`, `question`처럼 표준 이름으로 자동 변환되고, 커닝은 영문·숫자 쌍에만 적용된다.

- 기호 시트는 `!`·`?`·`;`·`%`·`=`처럼 조각이 여러 개인 글자와 작은 점·따옴표가 많아서 segment의 자동 병합·행 필터가 자주 틀린다(이웃 기호를 한 덩어리로 합치거나 작은 행을 통째로 버림). count가 예상과 다르면 contact sheet로 확인하고, 틀렸으면 연결요소를 직접 뽑아 번호를 붙인 이미지를 보고 글자별로 조각을 묶어 `comps.json`/`crops/`를 직접 만든다(형식은 segment 결과와 같게: i, row, x0..y1, baseline, cropW, cropH, offX, offY). 숫자가 대문자보다 작게 그려진 시트처럼 시트 간 크기를 맞춰야 하면 이미지를 먼저 배율 조정한다.
- 시트에 없는 기호는 있는 조각으로 조합할 수 있다: `"` = 따옴표 두 개, `:` = 점 두 개, `.` = 점, `,` = 쉼표.
- 시트상의 배치는 타이포 위치와 다르다. 빌드 후 project.json에서 위치를 보정하고 `node pipeline.js rebuild <project.json> <out.otf>`로 다시 만든다(cap 700 기준): `- + = ~ < > *`는 세로 중심 ≈340, 따옴표 류는 윗끝 ≈705, `_`는 윗끝 ≈-60, `[ ]`는 `( )` 높이에 맞춤. 마지막 줄 글자가 유난히 작게 그려진 시트가 많으니(XYZ 등) 높이도 확인하고, 보정했으면 사용자에게 알린다.
- 대문자만 있는 시트면 a–z에 대문자 글리프를 복사해 넣어 소문자로 쳐도 보이게 해준다(사용자에게 알릴 것). 커닝도 소문자·대소문자 섞인 쌍으로 복제해 `apply_kerning.py`로 넣는다.

## 3단계 — 폰트 빌드 + 품질 검수

### 윤곽 닫힘 — "시작점 뾰족 튀어나옴" 버그는 pipeline.js에 수정돼 있음

S 맨 위처럼 둥글어야 할 곳에 가시가 생기던 버그는 `loopsToPath`에서 모든 좌표를 정수로 넘기도록 고쳐져 있다(원인은 아래 엔지니어링 메모). 그래도 빌드할 때마다 아래 검사로 확인한다.

**닫힘 검사(빌드 후 QA에 항상 포함, 결과 0개여야 함)**:
```bash
python3 - /tmp/ff/font_final.otf <<'EOF'
import sys
from fontTools.ttLib import TTFont
from fontTools.pens.recordingPen import RecordingPen
gs=TTFont(sys.argv[1]).getGlyphSet(); bad=[]
for n in gs.keys():
    p=RecordingPen(); gs[n].draw(p); st=la=None
    for op,a in p.value:
        if op=='moveTo': st=a[0]
        elif op in('curveTo','lineTo','qCurveTo'): la=a[-1]
        elif op=='closePath' and st and la and max(abs(st[0]-la[0]),abs(st[1]-la[1]))>2: bad.append(n)
print('윤곽 닫힘 어긋난 글리프:', len(bad), bad[:10])
EOF
```

```bash
node pipeline.js build /tmp/ff/work /tmp/ff/labels.json "<폰트이름>" /tmp/ff/font.otf /tmp/ff/project.json
```

빌드 후 Mac/Windows 호환성 정리와 검증을 반드시 거친다:

```bash
PSNAME=$(node -e "
const opentype=require('./opentype.min.js');
const b=require('fs').readFileSync('/tmp/ff/font.otf');
const f=opentype.parse(b.buffer.slice(b.byteOffset,b.byteOffset+b.length));
console.log(f.names.postScriptName.en);
")
python3 fix_mac_names.py /tmp/ff/font.otf "$PSNAME" "<폰트이름>" /tmp/ff/font_final.otf
fontbakery check-opentype /tmp/ff/font_final.otf --loglevel FAIL 2>&1 | grep -c "Result: FAIL"   # 0이어야 함
python3 -c "from ots import sanitize; print('OTS:', 'PASS' if sanitize('/tmp/ff/font_final.otf', check=False, capture_output=True).returncode==0 else 'FAIL')"
python3 render_preview.py /tmp/ff/font_final.otf /tmp/ff/qc.png "<폰트이름>"
```

**qc.png를 view로 직접 확인**한다. 다만 **이 환경에서는 세션에 따라 view로 렌더링 이미지를 실제로 확인하는 게 안 될 때가 있다.** 이럴 땐 구조적 진단(아래 "구조적 QA" 절)으로 최대한 확인하고, 그걸로도 결함이 안 잡히면 솔직히 "내가 못 보고 있다"고 사용자에게 인정한 뒤 문제 부분을 표시한 확대 스크린샷을 요청한다 — 보이지도 않는 걸 봤다고 하거나 추측성 수정을 남발하지 말 것.

## 4단계 — 결과물 전달

1. `/mnt/user-data/outputs/`로 복사: `<폰트이름>.otf` + `<폰트이름>_project.json` (project.json은 이후 글자 교체·재조정에 필요하니 **꼭 함께 전달**하고 보관하라고 안내). 두 파일을 zip으로도 묶어 함께 전달(otf 직접 다운로드가 막히는 환경 대비).
2. **HTML 미리보기 아티팩트** (`make_preview.py` 사용): otf를 base64로 인라인 임베드한 단일 파일.
   - `preview_template.html`(assets 폴더)을 기반으로 생성됨. 구성:
     - 상단 "Image to Font Skill" 타이틀
     - 폰트 이름을 그 폰트로 크게 렌더링 + 전체 글자표(실제 폰트에 든 대문자·소문자·숫자·기호 줄, 개수 포함)
     - 사용자가 정한 샘플 문구 1줄
     - **직접 써보기(Type Tester)** — 입력칸 + 크기(16–160px)·자간 슬라이더. 샘플 카드 아래, 다운로드 카드 위
     - [폰트 파일(.otf) 다운로드] 버튼 — 로컬에서 연 HTML이면 .otf를 바로 저장, Claude 아티팩트 뷰어에서는 `downloads` 기능으로 `<이름>.zip`(안에 .otf)을 저장한다(뷰어는 페이지의 직접 다운로드를 막고 .otf 확장자도 허용하지 않음). **아티팩트로 게시할 때 `{downloads: true}` 기능을 선언해야** 버튼이 작동한다 — 선언 안 하면 눌러도 무반응.
     - **"바꾸고 싶은 글자가 있나요?" 안내 카드** — 이 HTML 안에서 첨부·수정하는 기능이 아니라, "이 대화창으로 돌아와서 글자 이미지를 첨부해달라"는 정적 안내문이다(버튼·JS 없음, 정적 텍스트만). 글자 교체는 채팅 기반으로만 처리한다 — HTML 안에 파일 첨부/드래그드롭/zip 다운로드 기능을 절대 넣지 말 것(예전에 넣었다가 복잡성만 늘고 실제로는 안 쓰였음).
     - 하단 `© @사용자핸들` 저작권 + "활용/공유 시 출처 태그 요청" 문구
   - 미리보기는 아티팩트로 게시하는 것과 별개로 **HTML 파일 자체도 항상 함께 전달**한다 (otf·project.json·zip과 같이 보내기). 다운로드 기능 선언이 안 되는 환경이면 폰트는 채팅의 파일 카드로 받으라고 안내한다.
3. 파일 전달(.otf, project.json, zip, **preview.html**) + 몇 자 인식됐는지, 빠진 글자, 설치법(.otf 더블클릭) 요약.
4. **전달 메시지 마지막에 반드시 물어볼 것** (둘 다 한 번에 물어봐도 된다):
   - "모양이 이상하거나 바꾸고 싶은 글자가 있으면 그 글자의 확대 이미지를 이 대화에 첨부해 주세요 (글자 높이 150px 이상 권장)."
   - "자간이나 글자 모양 등 그 밖에 수정하고 싶은 부분이 있으신가요?"
   사용자가 이미지를 첨부하면 아래 "글자 교체(patch)" 절차로, 자간 피드백을 주면 캐시된 `/tmp/ff/work`로 상수만 조정해 재빌드한다(이미지 재업로드 불필요).

## 글자 교체 (patch) — 특정 글자만 고해상 이미지로 재작업

사용자가 특정 글자가 마음에 안 든다며 그 글자의 큰 이미지를 올리면:

```bash
python3 img2bin.py <확대이미지> /tmp/ff/patch.bin    # 출력: W H
node pipeline.js patch <project.json 경로> /tmp/ff/patch.bin <W> <H> <글자> /tmp/ff/font.otf /tmp/ff/project.json
```

- project.json은 사용자가 첨부했거나(이전 세션) 같은 세션의 /tmp에 있음. 없으면 요청할 것.
- **patch는 "이미지 전체의 잉크 = 글자 하나"로 취급한다** (연결요소 기준 최대 조각만 고르지 않음). 이래야 O 안의 소용돌이 장식처럼 획과 떨어진 디테일도 온전히 살아남는다 — 예전엔 최대 조각 하나만 골라서 이런 디테일이 통째로 사라지는 버그가 있었다.
- 한 이미지에 여러 글자가 붙어 있으면(예: "Z"와 "H"가 나란히) 열 방향 잉크 밀도가 0에 가까운 지점을 자동으로 찾아 분리한 뒤 각각 patch한다.
- 기존 글자의 높이·최저점(오버슈트/디센더 포함)에 자동 정렬되므로 크기 걱정 불필요. 교체 후 재빌드 → QA(fontbakery/OTS) → 미리보기 갱신 → 재전달.
- 폰트에 없던 g/j/p/q/y류 소문자를 patch로 신규 추가하는 것은 기준선 추정이 불가해 거부됨 — 전체 시트로 만들라고 안내.

## 자간·글자 모양 미세 조정 (재업로드 없이 처리)

원본 세그먼트가 `/tmp/ff/work`(또는 병합본 `work_merged`)에 캐시돼 있으면, `pipeline.js`의 상수만 조정해서 `node pipeline.js build ...`를 다시 돌리면 된다. 조정 가능한 지점(모두 `build` 명령 안):

- **기본 자간(사이드베어링)**: `LSB` 계산식의 배율(현재 0.66) — 낮추면 전체적으로 더 좁아짐
- **단어 간격(스페이스 폭)**: `spaceAdv` 계산식의 배율(현재 LSB×5.4)
- **커닝 강도**: 트리거 임계값(현재 -3)과 최대 당김폭(현재 -190) — 트리거를 더 완화하면(예: -1) 더 많은 쌍이 당겨짐
- **광학 사이드베어링(좌우 독립)**: `edgeCurviness`가 측정한 leftStd/rightStd가 임계값(cropW×0.02)을 넘는 쪽만 축소(현재 72%). **반드시 좌우 독립으로 계산해야 한다** — 한쪽만 곡선인 글자(j의 왼쪽 고리는 곡선, 오른쪽 점/기둥은 직선 등)에 좌우 동일 값을 쓰면 반대쪽까지 억울하게 좁아지는 문제가 실제로 있었다("j가 뒷글자와 붙어 보인다"는 피드백으로 발견).
- **글자별 광학 오버슈트**: 위/아래 끝의 "평평함 비율"(끝에서 얇은 밴드 폭 ÷ 조금 안쪽 밴드 폭, 세리프 브래킷을 지난 지점부터 측정, 현재 `H*0.03`/`H*0.15` 지점·임계값 0.62)로 topFlat/botFlat을 자동 판정. 평평한 글자(순수 flat)는 배율 1.0, 한쪽만 평평하면 1+OVERSHOOT_HALF, 둘 다 아니면 1+OVERSHOOT_ROUND를 원래 `scale`에 곱한다(현재 각각 0.7%/1.2%). `DEBUG_SHAPE=1 node pipeline.js build ...`로 글자별 topFlat/botFlat/nativeH를 stderr로 확인 가능.
- **x-height 자연 군집화**: 어센더/디센더 유무와 무관하게(디센더 여부로 후보를 거르면 안 됨 — nativeH는 baseline~top 거리라 디센더와 무관) 소문자 전체의 `nativeH`를 정렬해 가장 큰 간격(gap)을 찾고, 그 아래쪽 군집(전체의 35% 이상일 때만 채택)만 골라 공통 기준 높이로 정밀 정렬한다. v,w,x,y,z처럼 미세한 상단 높이 편차가 남는 순수 x-height 글자들의 정렬에 쓴다.

**절대 하면 안 되는 것 — 실제로 있었던 심각한 버그**: "x-height 기준 목표 높이로 모든 소문자를 강제 재조정"하는 방식은 **절대 쓰지 말 것**. 어센더(b,d,f,h,i,j,k,l 등)까지 x-height 기준으로 눌러버려서 원본보다 훨씬 작아지는 사고가 났었다("장난해?"라는 반응으로 즉시 롤백 요구받음). 올바른 방식: 원본 이미지의 전역 `scale`은 절대 건드리지 않고, 개별 글자에는 그 글자 자신의 스케일에 아주 작은 배율(1.007~1.012 등)만 곱해서 살짝 키우는 정도로 그친다. x-height 군집화도 군집 밖 글자(어센더 등)는 절대 포함시키지 않도록 설계돼 있다.

**원본 이미지 자체의 실제 크기 차이**(예: 특정 글자가 시트에서 실제로 더 크게 그려진 경우)는 알고리즘으로 고치는 영역이 아니다 — 사용자에게 원본이 의도한 디자인인지 확인받을 것.

**폰트 안의 특정 글자를 다른 글자에서 파생시켜 달라는 요청**(예: "소문자 s를 대문자 S 축소판으로")은 **그 요청 자체를 스킬의 표준 기능으로 넣지 말 것** — 명시적으로 "이번 한 번만 적용, 스킬 로직에는 넣지 말라"는 지시를 받은 적이 있다. 필요하면 project.json을 직접 조작하는 일회성 후처리 스크립트로 처리하고(대상 글리프의 loops를 복사해 목표 높이로 스케일 후 좌표 재배치), pipeline.js의 `build` 로직 자체는 건드리지 않는다.

## 구조적 QA (view로 직접 확인이 안 될 때)

렌더링 이미지를 못 보는 세션에서는 project.json의 glyphs 데이터를 직접 열어 다음을 확인할 수 있다:

- **윤곽선 감김 방향**: 외곽선과 속공간(카운터) 루프의 부호 있는 면적(signed area, shoelace formula)이 서로 반대 부호인지 확인 — 같으면 렌더링 시 속공간이 안 뚫려 보일 수 있다.
- **자기교차**: 루프 안의 비인접 세그먼트끼리 교차하는지 O(n²) 검사.
- **이상 세그먼트**: 평균 세그먼트 길이의 4배 이상이거나 0.5 미만인 구간(단, 직선 기둥처럼 정상적으로 긴 구간도 있으므로 참고용).
- **높이/자간 실측**: fontTools의 `BoundsPen`, `hmtx` 테이블로 특정 글자들의 top/bottom/advance/RSB를 뽑아 목표치와 비교. `uharfbuzz`로 실제 셰이핑 폭(커닝 반영)도 측정 가능.

이런 진단으로도 안 잡히는 문제(예: "글자 일부가 뜯겨나간 것처럼 보인다")는 정직하게 "구조상 결함은 없는데, 이 환경에서 렌더링을 직접 못 보고 있다"고 인정하고 확대 스크린샷을 요청할 것.

## 엔지니어링 메모

- 메트릭: unitsPerEm 1000, ascender 760, descender -240 (**합이 반드시 1000** — 어기면 전 글자가 수직으로 밀린다)
- 대문자·숫자 높이 중앙값 → 700 정규화. 행 기준선 = 그 행 바닥 y의 중앙값 (오버슈트·디센더가 자연히 음수로 보존됨)
- 병합 규칙: 작은 조각(면적 30% 미만)만 큰 조각에 흡수 — i·j의 점, 끊긴 헤어라인용. 글자끼리는 절대 병합 금지 (플러리시 디센더가 아랫줄 글자를 삼키는 사고 방지)
- 행 필터: 면적 상위 조각들의 높이 중앙값(bigH) 기준 0.5~1.28배 밖의 행 제거 (헤더/설명/초대형 샘플 행). 이 필터도 완벽하지 않으니 count가 표준이 아니면 반드시 contact sheet를 눈으로 볼 것
- 중복 라벨은 첫 번째 것만 사용됨
- **em 좌표 반올림 계단 현상(수정됨)**: 픽셀 좌표를 최종 em 단위(보통 5~6배 확대)로 변환할 때 점마다 독립적으로 반올림하면, 원본에서 완벽히 일직선이던 구간도 미세하게 어긋나 계단처럼 보일 수 있다. `glyphFromCrop`은 반올림 직후 아주 작은 허용오차(2.2유닛)로 한 번 더 단순화해서 이 잔여 지그재그를 제거한다. 이 문제는 해상도를 올려도 저절로 없어지지 않는다(오히려 확대 배율이 커질수록 더 잘 드러남).
- **윤곽선 스무딩**: `traceBinary`가 픽셀 경계를 걸으면서 생기는 계단식 노이즈를 `smoothPolyline`(코너 보존형, 꺾임각 71도 미만인 점만 이웃 평균으로 완화)으로 `rdpClosed` 단순화 전에 먼저 제거한다. 코너 판정 임계값도 71도로 완화해 진짜 꺾인 부분(세리프 브래킷 등)만 각지게 남기고 나머지는 곡선으로 처리한다.
- **윤곽 시작점 뾰족 튀어나옴(수정됨, 2026-11)**: S 맨 위처럼 둥글어야 할 곳에 가시가 생기던 오래된 버그. 원인은 테두리 다듬기·해상도가 아니라 **파일로 저장하는 단계**였다 — `loopsToPath`가 중점·베지어 제어점을 소수점으로 넘기면 opentype.js가 CFF에 상대좌표를 점마다 반올림해서 써서, 오차가 한 바퀴 동안 쌓여 끝점이 시작점에서 5~15유닛 어긋나고 closePath가 그 틈을 직선으로 이어 가시가 됐다(거의 모든 글자에 있었고 점이 많은 S에서 가장 눈에 띔). 지금은 모든 좌표를 정수로 반올림해서 넘긴다. project.json만 봐서는 절대 안 보이므로, 의심되면 "닫힘 검사"처럼 **최종 .otf의 그리기 명령을 직접** 확인할 것.
